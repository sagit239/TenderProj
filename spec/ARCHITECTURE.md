# Architecture

> הארכיטקטורה הטכנית למימוש מערכת ניהול המכרזים, בהתבסס על `PRD.md`. התכנון פשוט ככל האפשר. כל השירותים פועלים במסלול חינמי, מלבד שירות ה-AI (OpenAI), שמשלמים עליו לפי שימוש עם תקרה חודשית. זה החריג שאושר ב-PRD.

## 1. Technology Stack שנבחר

| רכיב | טכנולוגיה | תפקיד |
|------|-----------|-------|
| Frontend + Backend | Next.js 16 (App Router) + TypeScript | ממשק המשתמש (עברית, RTL, Responsive) ו-Route Handlers בצד השרת: ניתוח, ייצוא, מיילים ותזכורות |
| עיצוב | Tailwind CSS | עיצוב Responsive ותמיכה מובנית ב-RTL |
| Database | Supabase (PostgreSQL) | נתוני המכרזים, תוצאות הניתוח, המשימות, אנשי הצוות והתזכורות |
| אחסון קבצים | Supabase Storage (Bucket פרטי) | שמירת מסמכי המכרז המקוריים |
| Authentication | Supabase Auth (מייל + סיסמה) | התחברות של המשתמשת היחידה |
| ניתוח מסמכים (AI) | OpenAI API (Responses API), מודל `gpt-6.1-sol` (נקבע סופית בבדיקה המקדימה של M3), דרך ספריית `openai` | הפקת סיכום, מועדים, משימות וסעיפים בעייתיים מתוך מסמכי המכרז |
| המרת קבצים | `mammoth` (Word ‏docx), ‏`word-extractor` (Word ישן ‏doc) ו-`xlsx` / SheetJS (Excel) | המרת Word ו-Excel לטקסט. PDF, כולל סרוק, נשלח ל-OpenAI כמו שהוא |
| שליחת מיילים | Gmail SMTP דרך `nodemailer` | תזכורות, התראות על כשלים ושליחת סיכומים מחשבון Gmail ייעודי לפרויקט. אפשר להחליף בעתיד ל-Outlook או לספק אחר בשינוי הגדרות ב-`lib/email` בלבד |
| חגים וימי עבודה | `@hebcal/core` (בזמן פיתוח בלבד) | הפקת רשימת החגים בישראל לשנים הקרובות, שנשמרת בטבלת `holidays` |
| תזמון תזכורות | Supabase `pg_cron` + `pg_net` | קריאה כל 15 דקות ל-Endpoint ששולח את התזכורות שהגיע זמנן |
| ייצוא Word | ספריית `docx` | קובץ Word בעברית (RTL) |
| ייצוא PDF | עמוד הדפסה ייעודי + "שמירה כ-PDF" בדפדפן | PDF בעברית בלי ספריית PDF בצד השרת |
| Hosting | Vercel | אחסון האפליקציה ופריסה אוטומטית מ-GitHub |
| קוד המקור | Git Repository ב-GitHub | אחסון הקוד והיסטוריית הגרסאות |

### החלטות טכנולוגיות מרכזיות
- **Next.js על Vercel.** יש צורך ב-Backend: מפתחות סודיים ל-AI ולמייל, ניתוח שנמשך דקות ותזכורות מתוזמנות. Next.js מאחד ממשק ושרת בפרויקט אחד, ו-Vercel מתחבר ל-GitHub ופורס אוטומטית. בתוכנית החינמית זמן הריצה המקסימלי לפונקציה הוא 300 שניות, וזה מספיק לניתוח מכרז. החלופה שנבחנה: Netlify. בתוכנית החינמית שלו מגבלת זמן הריצה קצרה בהרבה (עשרות שניות), ולכן הוא לא מתאים לניתוח.
- **Supabase.** משלב Database רלציוני, Auth ו-Storage בשירות אחד. התוכנית החינמית מאפשרת 2 פרויקטים פעילים, בדיוק Development ו-Production. נתוני המוצר רלציוניים (מכרז ← מסמכים, מועדים, משימות ← תזכורות), ולכן PostgreSQL מתאים ואין הצדקה ל-NoSQL. החלופה שנבחנה: Firebase. הוא NoSQL, ומידול הקשרים והשאילתות בו פחות פשוט.
- **OpenAI.** נבחר על ידי המשתמשת, שכבר יש לה מפתח API של OpenAI (ADR-15, במקום Claude שנבחר באפיון). ב-Responses API, ‏PDF נקרא גם כטקסט וגם כתמונה של כל עמוד, ולכן גם PDF סרוק נקרא. מידע שנשלח דרך ה-API אינו משמש לאימון מודלים כברירת מחדל. בכך מתקיימת דרישת הפרטיות שב-PRD. המודל `gpt-6.1-sol` הוא ברירת המחדל: ביצועים קרובים למודל המוביל, בחמישית מהמחיר. החלופות: `gpt-6.1-terra` (מהיר וזול יותר) ו-`gpt-6-astra` (המודל המוביל, יקר פי 5). מעבר ביניהם דורש שינוי של משתנה אחד. ההחלטה הסופית מתקבלת בבדיקה המקדימה של M3.
- **Gmail SMTP.** חינמי, לא דורש בעלות על דומיין, ומכסת השליחה של חשבון Gmail פרטי (כ-500 נמענים ביום) גבוהה בהרבה מהצורך. החלופות שנבחנו: שירותי מייל ייעודיים כמו Resend. במסלול החינמי הם דורשים דומיין מאומת כדי לשלוח לנמענים חיצוניים. כל השליחה מרוכזת ב-`lib/email`, ולכן מעבר עתידי ל-Outlook (למשל חשבון Microsoft 365 של הארגון) הוא שינוי הגדרות ושינוי קוד קטן, בלי השפעה על שאר המערכת.
- **`pg_cron` לתזכורות.** ב-Vercel Hobby, Cron רץ רק פעם ביום, ובדיוק של עד שעה. תזכורת "3 שעות לפני הגשה" דורשת בדיקה תכופה. `pg_cron` ב-Supabase חינמי ומאפשר הפעלה כל 15 דקות. החלופה שנבחנה: GitHub Actions. ההפעלות המתוזמנות שם עלולות להתעכב בעשרות דקות.
- **PDF דרך הדפסת הדפדפן.** יצירת PDF בעברית בצד השרת דורשת טיפול בגופנים ובכיווניות. עמוד הדפסה מעוצב פשוט ואמין יותר.

### סיכונים ומגבלות
- **Vercel Hobby מיועד לשימוש אישי ולא מסחרי.** לפי תנאי Vercel, שימוש לטובת רווח כספי של מישהו (גם ארגון) נחשב מסחרי ודורש תוכנית Pro, בכ-‎$20 לחודש. זו שאלה של תנאי שימוש, לא של יכולת טכנית. מבחינה טכנית המערכת זהה בשתי התוכניות, והמעבר הוא שינוי בחשבון בלבד, בלי שינוי קוד.
- **עלות OpenAI.** ‏`gpt-6.1-sol` עולה ‎$2 למיליון Tokens קלט ו-‎$10 למיליון Tokens פלט (נובמבר 2026). הערכה: פחות מ-‎$1 לניתוח מכרז של 60 עמודים, וכמה דולרים בחודש ב-5–10 מכרזים, כולל ניתוחים חוזרים. העלות המדויקת נמדדת בבדיקה המקדימה. בחשבון OpenAI מגדירים תקרת הוצאה חודשית (Budget).
- **השהיית פרויקט ב-Supabase.** פרויקט חינמי מושהה אחרי 7 ימים ללא פעילות. קריאת התזכורות כל 15 דקות פונה ל-Database דרך ה-API, ולכן היא אמורה להיחשב פעילות ולשמור על פרויקט ה-Production ער. פרויקט ה-Development עלול להיות מושהה בתקופות בלי פיתוח, ומחזירים אותו בלחיצה בלוח הבקרה. הנתונים נשמרים, ואפשר לשחזר עד שנה.
- **זמן ניתוח.** ניתוח מכרז ארוך נמשך כמה דקות, וכתיבת תשובה ארוכה במודל המתקדם עלולה לקרב אותו למגבלת 300 השניות. לכן בתחילת Milestone 3 מתבצעת בדיקה מקדימה על מכרז אמיתי, שמודדת זמן ועלות ובודקת את מגבלות ה-API (מספר עמודים לבקשה, מחירים, שילוב Files API עם Structured Outputs ו-Streaming). אם הזמן חורג, עוברים ל-`gpt-6.1-terra` או מפצלים את הבקשה. ניתוח שנמשך יותר מ-5 דקות מסומן כנכשל, עם אפשרות לנסות שוב.
- **דיוק ההפניות.** שם הקובץ, העמוד והסעיף שמוצגים לכל ממצא מופקים על ידי ה-AI, ולפעמים הם לא מדויקים. ההפניה מוצגת כדי לאפשר אימות מול המקור. בקובצי Word ו-Excel אין עמודים, ולכן ההפניה היא לסעיף או לגיליון.
- **שמירה זמנית אצל OpenAI.** בקשות ל-API נשמרות אצל OpenAI עד 30 יום לצורך ניטור שימוש לרעה, גם אם הקבצים נמחקים מ-Files API. ה-PRD מתיר שמירה זמנית אצל ספק ה-AI, כי נשלחים רק מסמכים פומביים.
- **Gmail** עלול לחסום זמנית חשבון חדש ששולח מיילים רבים בבת אחת. בהיקף הצפוי זה לא צפוי לקרות. מיילים מחשבון Gmail לא מוכר עלולים להגיע לתיקיית הספאם בתיבות של הארגון, ולכן בודקים זאת מוקדם, ב-Milestone 5, מול כתובת אמיתית של עובד. כתובת המענה (Reply-To) של כל מייל היא הכתובת של המשתמשת (`NOTIFY_EMAIL`).
- **אין גיבויים אוטומטיים.** במסלול החינמי של Supabase אין גיבויים שאפשר להוריד. במקרה של תקלה חמורה הנתונים עלולים לאבד. אפשרות פשוטה בהמשך: ייצוא ידני תקופתי של הנתונים.
- **נפח אחסון.** קובצי PDF סרוקים גדולים, ולכן ה-1GB החינמי מספיק לכמה עשרות מכרזים, לא לכמה מאות. כשהנפח יתקרב לסוף: אפשר למחוק את הקבצים של מכרזים ישנים מהארכיון ולהשאיר את הניתוח שלהם, או לעבור לתוכנית בתשלום.

## 2. ארכיטקטורת המערכת

### מבנה המערכת
```
דפדפן (מחשב / נייד)
   │  ממשק עברי RTL
   ▼
Next.js על Vercel ───────────► OpenAI API   (ניתוח מסמכים)
   • דפים                    ─► Gmail SMTP   (מיילים)
   • Route Handlers
   │
   ▼
Supabase
   • Auth      – התחברות
   • Postgres  – נתונים
   • Storage   – קבצי המכרז
   • pg_cron ──(כל 15 דק')──► Route Handler לשליחת תזכורות
```

| רכיב | אחריות |
|---|---|
| דפדפן | הצגת הממשק. קריאה וכתיבה ישירה ל-Supabase בפעולות פשוטות. העלאת קבצים ישירות ל-Storage |
| Next.js – צד שרת | פעולות שדורשות סודות או זמן ריצה ארוך: ניתוח AI, שליחת מיילים, ייצוא Word, תזכורות |
| Supabase | אחסון כל הנתונים והקבצים, אימות משתמשת, הרשאות (RLS) ותזמון |
| OpenAI API | ניתוח המסמכים בלבד |
| Gmail | שליחת המיילים בלבד |

### Modules ושכבות
- **ממשק (`app/`):** דפים לפי ה-User Flows שב-PRD: התחברות, איפוס סיסמה, מכרזים פעילים, מכרז חדש, מסך מכרז (לשוניות: סיכום, לוח זמנים, משימות, סעיפים בעייתיים, מסמכים), ארכיון, הוגשו לפי מחלקה, אנשי צוות, ועמוד הדפסה.
- **שרת (`app/api/`):** Route Handlers. ראו "APIs ואינטגרציות".
- **לוגיקה עסקית (`lib/`):**
  - `ai`: בניית הבקשה ל-OpenAI, ה-Prompt והסכמה של התשובה. זו נקודת המגע היחידה עם ה-AI.
  - `files`: שליפה מ-Storage והמרת Word ו-Excel לטקסט.
  - `reminders`: כללי התזמון לפי סוג משימה, ימי עבודה (בלי שישי, שבת וחגים), יצירה, ביטול ותזמון מחדש.
  - `email`: שליחה ותבניות מייל (עברית, RTL).
  - `db`: יצירת לקוחות Supabase, אחד לדפדפן ואחד לשרת.
- **נתונים (`supabase/migrations/`):** קובצי SQL שמגדירים את מבנה ה-Database, את ה-RLS ואת ה-Bucket.

הממשק פונה ל-`lib` ול-Supabase. ה-Route Handlers משתמשים ב-`lib`. רק `lib/ai` פונה ל-OpenAI, ורק `lib/email` פונה ל-Gmail.

### Frontend ו-Backend
- **Frontend:** רכיבי React ב-Next.js, עם `<html lang="he" dir="rtl">`, וממשק Responsive למחשב ולנייד. כל הדפים, מלבד דף ההתחברות, מוגנים, ומשתמשת שלא התחברה מועברת לדף ההתחברות.
- **פעולות ישירות מהדפדפן מול Supabase:** קריאת נתונים, עריכה, שינוי סטטוס, שיוך משימות, סימון "בוצע", ניהול אנשי צוות, העלאת קבצים, מחיקת קבצים ומחיקת מכרז (קודם הקבצים מ-Storage, ואז הרשומה). הפעולות מוגנות ב-RLS.
- **Backend (Route Handlers):** רק פעולות שדורשות סוד או זמן ריצה ארוך. יצירה, ביטול ותזמון מחדש של תזכורות נעשים ב-Database באמצעות Triggers. כך התזכורות מתעדכנות נכון בכל שינוי, לא משנה מאיפה הוא נעשה.

### Data Model

| טבלה | שדות עיקריים | הערות |
|---|---|---|
| `roles` | key, label, sort_order | רשימת התפקידים. מתחילה עם 6 התפקידים (`legal`, `accounting`, `team_manager`, `agent`, `division_manager`, `service_manager`), ואפשר להוסיף תפקידים מהממשק (ADR-12) |
| `team_members` | id, name, role, email | role: מפתח מטבלת `roles` |
| `tenders` | id, name, department, status, decided_at?, submitted_at?, analysis_status, analysis_started_at?, analysis_error, created_at | department: `medical` / `safety`. status: `reviewing`, `preparing`, `not_bidding`, `submitted`, `won`, `lost`. analysis_status: `idle`, `running`, `done`, `failed`. ‏decided_at נשמר במעבר ל-`not_bidding`, ו-submitted_at במעבר ל-`submitted` (ונשאר גם ב-`won` / `lost`) |
| `tender_documents` | id, tender_id, file_name, storage_path, file_type, read_warning, analyzed_at | read_warning: קובץ שלא נקרא או נקרא חלקית |
| `requirements` | id, tender_id, text, sort_order, is_manual | פריטי סיכום הדרישות |
| `deadlines` | id, tender_id, type, title, due_at, has_time, source_refs, is_manual, is_auto | type: `submission`, `bidders_meeting`, `clarification_questions`, `closing_meeting`, `other`. ‏has_time = false: מועד בלי שעה. ‏is_auto: פגישת סגירת פינות שנוצרה אוטומטית |
| `tasks` | id, tender_id, deadline_id?, title, type, due_at, has_time, is_done, remind_at?, reminders_off, is_manual, source_refs | type: סוגי המועדים, ובנוסף `regular`. ‏deadline_id מולא = המשימה בלוח הזמנים. ‏due_at במשימה בלי deadline_id = תאריך מהמכרז, לקריאה בלבד, ו-source_refs שומר את המקור שלו. ‏remind_at מיועד ל-`other`. ‏reminders_off = "ללא תזכורת": לא נוצרות תזכורות למשימה. במשימה שמקושרת למועד, ‏due_at ו-has_time מסונכרנים עם המועד |
| `task_assignees` | task_id, team_member_id | אחראי אחד או יותר לכל משימה (N:N) |
| `issues` | id, tender_id, category, title, explanation, source_refs, suggested_question, is_manual | category: `threshold`, `guarantees`, `penalties`, `liability`, `insurance`, `payment_terms`, `one_sided`, `contradictions` |
| `analysis_runs` | id, tender_id, started_at, finished_at, status, change_report | כל ריצת ניתוח. ‏change_report: דוח השינויים מול הגרסה הקודמת (JSON) |
| `analysis_proposals` | id, run_id, tender_id, item_type, payload, status | פריטים חדשים מניתוח חוזר שממתינים לאישור. status: `pending`, `accepted`, `rejected` |
| `reminders` | id, task_id, team_member_id?, send_at, kind, status, sent_at, error | team_member_id ריק = תזכורת למשתמשת (`NOTIFY_EMAIL`). כתובת המייל נשלפת ברגע השליחה. kind: `scheduled` / `followup` / `self`. status: `pending`, `sent`, `cancelled`, `failed` |
| `holidays` | date, name | חגים בישראל שאינם ימי עבודה, לשנים הקרובות. נטען ב-Migration |
| `app_migrations` | name, applied_at | רישום ה-Migrations שהורצו בכל סביבה |

**`source_refs`:** רשימה (JSON) של הפניות, כל אחת עם `file_name`, `page` ו-`section`. בסתירה בין מסמכים יש שתי הפניות או יותר. בקובצי Word ו-Excel ‏`page` ריק, ו-`section` מכיל את הסעיף או את שם הגיליון.

**קשרים:**
- מכרז ← מסמכים, דרישות, מועדים, משימות, סעיפים בעייתיים, ריצות ניתוח והצעות (1:N, מחיקה מדורגת).
- משימה ← תזכורות (1:N, מחיקה מדורגת).
- משימה ↔ איש צוות (N:N דרך `task_assignees`. מחיקת איש צוות מסירה אותו מהמשימות).
- משימה → מועד (N:1, אופציונלי).

**כללים:**
- "באיחור" מחושב בתצוגה (`due_at < now()` ו-`is_done = false`), ולא נשמר.
- "זכינו" מוצג בסימון בולט לפי `status = 'won'`.
- "ארכיון" (`not_bidding`) ו"הוגשו" (`submitted`, `won`, `lost`, לפי `department`) הם תצוגות מסוננות, ולא טבלאות נפרדות.
- `is_manual = true` מסמן פריט שהמשתמשת יצרה או ערכה (ומוצג כ"ידני"). ניתוח מחדש **לעולם לא משנה ולא מוחק** פריטים קיימים, ידניים או לא.
- **סנכרון משימה ומועד:** Trigger מעדכן את המועד כשמשנים את התאריך במשימה המקושרת, ואת המשימות המקושרות כשמשנים את המועד.
- **פגישת סגירת פינות:** Trigger על מועד ההגשה יוצר מועד `closing_meeting` (‏`is_auto`, בלי שעה) 3 ימי עבודה לפני ההגשה, ומשימה מקושרת "פגישת סגירת פינות". שינוי מועד ההגשה מזיז את הפגישה, אלא אם המשתמשת ערכה אותה (`is_manual`). ימי עבודה: לא שישי, לא שבת ולא תאריך מטבלת `holidays`.
- **מועד בלי שעה:** נשמר ב-`due_at` בשעה 08:00 שעון ישראל, עם `has_time = false`, ומוצג בלי שעה.
- כל הזמנים נשמרים ב-UTC (`timestamptz`), ומוצגים ומחושבים לפי `Asia/Jerusalem`.

### APIs ואינטגרציות

**Route Handlers:**

| Endpoint | תפקיד |
|---|---|
| `POST /api/tenders/[id]/analyze` | ניתוח, או ניתוח מחדש, של כל מסמכי המכרז ושמירת התוצאות (`maxDuration = 300`) |
| `GET /api/tenders/[id]/export/docx` | יצירת קובץ Word של הסיכום |
| `POST /api/tenders/[id]/email` | שליחת התוכן שנערך בחלון "שליחה במייל" לנמען אחד או יותר |
| `POST /api/cron/reminders` | שליחת התזכורות שהגיע זמנן. מאומת בכותרת `Authorization: Bearer <CRON_SECRET>` |

כל Endpoint, חוץ מ-`cron`, מאמת שהבקשה מגיעה ממשתמשת מחוברת.

**OpenAI API (Responses API):**
- קובצי PDF מועלים ל-Files API של OpenAI (‏`purpose: user_data`) ומצורפים לבקשה כ-`input_file`. ‏Word ו-Excel נשלחים כטקסט אחרי המרה, בתוך הבקשה, עם שם הקובץ המקורי. נשלחת בקשה אחת עם כל המסמכים, כדי שאפשר יהיה לזהות סתירות בין מסמכים. אחרי הניתוח הקבצים נמחקים מ-OpenAI, ובנוסף הם מועלים עם תפוגה אוטומטית (`expires_after`), כגיבוי למקרה שהמחיקה נכשלה.
- התשובה נדרשת כ-JSON במבנה קבוע (Structured Outputs, ‏`json_schema` עם `strict`): `requirements[]`, `deadlines[]`, `tasks[]`, `issues[]`. כל מועד וסעיף בעייתי כולל הפניות למקור: שם קובץ, עמוד וסעיף. כל מועד כולל סימון אם צוינה בו שעה.
- בניתוח חוזר נשלחים ל-OpenAI גם הפריטים הקיימים (רק הטקסט שלהם, בלי שמות אנשי צוות). המודל מחזיר את הפריטים החדשים ואת הפריטים הקיימים שלא נמצאו שוב, והם הבסיס להצעות ולדוח השינויים.
- הבקשה מתבצעת ב-Streaming, כדי למנוע ניתוק בבקשה ארוכה.
- מגבלות: עד 50MB לקובץ, ועד 50MB לכל הקבצים בבקשה אחת. מכרז רגיל (כמה MB) רחוק מהמגבלה. מכרז עם סריקות כבדות שעובר אותה מקבל הודעת שגיאה ברורה.

**Gmail SMTP:** ‏`smtp.gmail.com`, פורט 465 (SSL), עם `GMAIL_USER` ו-`GMAIL_APP_PASSWORD`. דורש אימות דו-שלבי בחשבון.

**Supabase:** ספריית `@supabase/supabase-js` ו-`@supabase/ssr`, לניהול ההתחברות ב-Next.js.

### Data Flow

**העלאה וניתוח:**
1. המשתמשת יוצרת מכרז (שם ומחלקה). המכרז נשמר בסטטוס `reviewing`.
2. הקבצים עולים **ישירות מהדפדפן ל-Supabase Storage**, ולא דרך Vercel. כך נעקפת מגבלת גודל הבקשה של Vercel. המגבלה היא 50MB לקובץ.
3. הדפדפן קורא ל-`/analyze`. אם כבר רץ ניתוח (`running` שהתחיל לפני פחות מ-5 דקות), הבקשה נדחית. אחרת השרת מסמן `analysis_status = running` ואת `analysis_started_at`, ויוצר רשומת `analysis_runs`. הממשק מציג "בניתוח…", בלי אחוזים. ניתוח שנשאר `running` יותר מ-5 דקות מוצג כנכשל.
4. השרת שולף את הקבצים, ממיר Word ו-Excel, שולח את הכול ל-OpenAI ומקבל JSON.
5. **ניתוח ראשון:** הפריטים נשמרים ישירות. **ניתוח חוזר:** הפריטים הקיימים לא משתנים. הפריטים החדשים נשמרים ב-`analysis_proposals`, ונשמר דוח שינויים ב-`analysis_runs.change_report`. הממשק מציג את ההצעות לאישור, ופריט שאושר נוסף למכרז. ההצעות נשמרות ב-Database, כך שאפשר לאשר אותן גם אחרי סגירת הדפדפן.
6. `analysis_status = done`. אם קובץ לא נקרא, נשמר `read_warning`, והניתוח ממשיך עם שאר הקבצים.

**תזכורות:**
1. Trigger ב-Database יוצר, מבטל או מתזמן מחדש רשומות `reminders` בכל שינוי במשימה (מועד, אחראים, "בוצע", מועד תזכורת, "ללא תזכורת"), בכל שינוי במועד המקושר ובכל שינוי בסטטוס המכרז. נוצרת רשומה לכל אחראי. הכללים:

   | סוג משימה | תזכורות לאחראי המשימה |
   |---|---|
   | `submission` | 24 שעות לפני, 3 שעות לפני |
   | `bidders_meeting` | 3 ימים לפני, ובנוסף `followup` יום לפני |
   | `clarification_questions` | 24 שעות לפני |
   | `closing_meeting` | ב-08:00 ביום הפגישה |
   | `other` | אם `remind_at` מולא: תזכורת ב-`remind_at` לכל האחראים, ואם אין אחראי, תזכורת `self` למשתמשת. אחרת: יום לפני המועד, לאחראים בלבד (ADR-23) |
   | `regular` | אין תזכורות (ADR-24) |

   - **שישי, שבת וחגים:** תזכורת שזמנה יוצא ביום שישי, בשבת או בתאריך מטבלת `holidays` מוקדמת ליום העבודה הקודם, באותה שעה שבה הייתה אמורה לצאת (במועד בלי שעה, ב-08:00). התזכורת "3 שעות לפני" לא מוזזת.
   - **רק מה שבלוח הזמנים** (`deadline_id` מולא) מקבל תזכורות (ADR-24).
   - **ללא תזכורת** (`reminders_off = true`): לא נוצרות תזכורות למשימה, גם כשיש לה אחראים.
   - **מועד בלי שעה** (`has_time = false`): תזכורות לפי ימים נשלחות ב-08:00, ותזכורת "3 שעות לפני" לא נוצרת.
   - תזכורת שזמנה כבר עבר לא נוצרת.
   - סימון "בוצע", הסרת אחראי (לאותו אחראי), או מעבר המכרז ל-`not_bidding` או ל-`submitted` מבטלים את התזכורות הפתוחות (`cancelled`).
   - ביטול "בוצע" או שינוי מועד מתזמנים אותן מחדש.
2. כל 15 דקות `pg_cron` שולח, דרך `pg_net`, בקשה ל-`/api/cron/reminders`.
3. השרת שולף תזכורות `pending` שזמנן הגיע ושהמשימה שלהן לא בוצעה. כתובת המייל נשלפת עכשיו מ-`team_members` (או `NOTIFY_EMAIL`), כך ששינוי כתובת חל מיד. כל מייל כולל רק את המשימה הספציפית: שם המכרז, שם המשימה והמועד. השרת שולח ב-Gmail, עם Reply-To ל-`NOTIFY_EMAIL`, ומסמן `sent`.
4. אם השליחה נכשלה (כתובת לא תקינה, דחייה מיידית של השרת או תקלה), השרת מסמן `failed`, שומר את השגיאה ושולח מייל התראה ל-`NOTIFY_EMAIL`. מייל שנדחה מאוחר יותר (Bounce) מגיע לתיבה של `GMAIL_USER`, ומשם מועבר אוטומטית או נבדק ידנית.
5. הממשק מציג למשתמשת גם התראה על תזכורות שנכשלו.

**ייצוא ושליחה:**
- **Word:** השרת בונה קובץ ‎`.docx` מהנתונים השמורים, עם ארבעת החלקים: סיכום דרישות, לוח זמנים, משימות וסעיפים בעייתיים.
- **PDF:** עמוד הדפסה בדפדפן עם אותם ארבעה חלקים, ושמירה כ-PDF.
- **מייל:** הדפדפן מכין טיוטה מהחלקים שנבחרו, והמשתמשת עורכת אותה בחלון. השרת מקבל את הטקסט הערוך ואת רשימת הנמענים, בונה מייל HTML (RTL) ושולח אותו לכל הנמענים. העריכה לא נשמרת בנתוני המכרז.

### Authentication, Authorization, אבטחה ופרטיות
- **Authentication:** Supabase Auth עם מייל וסיסמה. המשתמשת נוצרת ידנית בלוח הבקרה של Supabase, וההרשמה הציבורית כבויה (`Allow new users to sign up = off`). Session נשמר ב-Cookies דרך `@supabase/ssr`.
- **איפוס סיסמה:** "שכחתי סיסמה" משתמש ב-`resetPasswordForEmail` של Supabase Auth, ומוביל לדף `/reset-password` לבחירת סיסמה חדשה. מיילי האיפוס נשלחים דרך אותו חשבון Gmail, שמוגדר כ-Custom SMTP ב-Supabase Auth, כי שירות המייל המובנה של Supabase מוגבל מאוד.
- **Authorization:** משתמשת אחת. RLS מופעל על כל הטבלאות, עם מדיניות שמאפשרת גישה רק ל-`authenticated`. Bucket ה-Storage פרטי, עם אותה מדיניות.
- **סודות:** `OPENAI_API_KEY`, `GMAIL_APP_PASSWORD`, `SUPABASE_SERVICE_ROLE_KEY` ו-`CRON_SECRET` קיימים רק בצד השרת: ב-`.env` המקומי וב-Environment Variables של Vercel. הם לעולם לא נשלחים לדפדפן ולא נשמרים ב-GitHub (`.env` נמצא ב-`.gitignore`).
- **פרטיות ה-AI:** ל-OpenAI נשלחים **רק מסמכי המכרז הפומביים** (ובניתוח חוזר גם הטקסט של הפריטים שהופקו מהם). שמות, מיילים, שם החברה, החלטות והערות של הארגון לא נשלחים ל-AI. OpenAI לא מאמנת מודלים על מידע מה-API כברירת מחדל. אסור להפעיל בחשבון את האפשרות לשתף מידע עם OpenAI לשיפור המודלים. הקבצים נמחקים מ-Files API אחרי כל ניתוח. OpenAI שומרת את הבקשות עד 30 יום, וה-PRD מתיר זאת.
- **Endpoint התזכורות** מאומת בסוד משותף, כך שאי אפשר להפעיל אותו מבחוץ.

### תשתיות, Hosting, Deployment ו-Configuration

**GitHub, ‏Build ו-Deployment:**
- הקוד נשמר ב-Repository ב-GitHub. פרויקט Vercel מחובר ל-Repository.
- כל Push לענף `main` מפעיל Build (`next build`) ופריסה אוטומטית ל-Production. אין פריסה ידנית.

המחשב המקומי מחובר ל-Development בלבד. אין הרצה מקומית של Supabase ואין Docker. כל הפיתוח נעשה מול פרויקט ה-Development בענן.

**חיבור ל-Database:** האפליקציה מתחברת דרך `NEXT_PUBLIC_SUPABASE_URL` ו-`NEXT_PUBLIC_SUPABASE_ANON_KEY` (גישה מוגבלת ב-RLS), ובצד השרת גם דרך `SUPABASE_SERVICE_ROLE_KEY`. ה-Service Role משמש למשל את Endpoint התזכורות. הרצת Migrations על Development נעשית דרך `SUPABASE_DB_URL`, שקיים רק ב-`.env` המקומי.

**נוהל Database Migrations:**
1. כל שינוי במבנה ה-Database נכתב כקובץ SQL חדש ב-`supabase/migrations/`, עם שם שמתחיל בתאריך. בסוף כל קובץ נרשמת שורה ב-`app_migrations`.
2. **Development:** ‏Claude מריץ את הקובץ על פרויקט ה-Development, באמצעות Supabase CLI עם `SUPABASE_DB_URL`, ובודק שהאפליקציה עובדת.
3. **Production:** לפני ה-Push ל-GitHub, Claude עוצר ומציג למשתמשת אילו Migrations עדיין לא הורצו על Production. ההשוואה נעשית מול `app_migrations` של Production.
4. אחרי אישור המשתמשת, הקובץ מורץ על Production. המשתמשת מדביקה את ה-SQL ב-SQL Editor של פרויקט ה-Production, לפי הדרכה צעד-אחר-צעד. כך פרטי הגישה של Production לא נשמרים במחשב.
5. רק אחרי ש-Production עודכן מתבצע ה-Push, וכך הפריסה לא מקדימה את עדכון ה-Database.

**הגדרות שאינן עוברות ב-Migrations, ושיש להגדיר בנפרד בכל פרויקט:**
- **Auth:** יצירת המשתמשת, כיבוי ההרשמה הציבורית, הגדרת Site URL (‏`http://localhost:3000` ב-Development, כתובת Vercel ב-Production), הוספת `/reset-password` ל-Redirect URLs, והגדרת Custom SMTP עם חשבון ה-Gmail (מ-Milestone 5).
- **הרחבות:** הפעלת `pg_cron` ו-`pg_net`, אם הן לא מופעלות דרך ה-Migration.
- **Cron Job:** כתובת ה-Endpoint ו-`CRON_SECRET` שונים בכל סביבה, ולכן ה-Job נוצר רק ב-Production, בסקריפט SQL נפרד שאינו ב-Migrations. הסוד נשמר ב-Supabase Vault.
- **סודות האפליקציה:** ב-`.env` המקומי (Development) וב-Vercel (Production).

### החלטות טכניות מרכזיות נוספות
- **אזור זמן:** כל חישובי התזכורות והתצוגה לפי `Asia/Jerusalem`.
- **בקשת AI אחת לכל מכרז:** כל המסמכים נשלחים יחד, לזיהוי סתירות ולתמונה שלמה.
- **ניתוח חוזר רק מוסיף:** הוא לא משנה ולא מוחק פריטים קיימים. פריטים חדשים מוצגים לאישור לפני שילובם, ונשמר דוח שינויים.
- **לוגיקת התזכורות ב-Database (Triggers):** כך התזכורות תמיד מסונכרנות עם מצב המשימה, לא משנה מאיפה בוצע השינוי.

## החלטות מרכזיות (ADRs)

### ADR-1: Claude כשירות ה-AI, כחריג בתשלום (הוחלף ב-ADR-15)
**הקשר:** לפי ה-PRD, המערכת צריכה לפעול ללא עלות, עם התחייבות לפרטיות מצד ספק ה-AI. מסלולי AI חינמיים עשויים להשתמש במידע לאימון.
**החלטה:** שימוש ב-Claude API (`claude-opus-5-5`), עם תשלום לפי שימוש ותקרת הוצאה חודשית. ההחלטה התקבלה על ידי המשתמשת ונרשמה ב-PRD.
**השלכות:** עלות מוערכת של כמה דולרים עד כ-‎$15 בחודש. איכות גבוהה בעברית ותמיכה ב-PDF סרוק. המידע לא משמש לאימון. אפשר לעבור ל-`claude-sonnet-5-5` בשינוי של משתנה סביבה.

### ADR-2: תזמון תזכורות דרך pg_cron ב-Supabase
**הקשר:** תזכורת "3 שעות לפני" דורשת בדיקה תכופה. ב-Vercel Hobby, Cron רץ פעם ביום, ובדיוק של עד שעה.
**החלטה:** ‏`pg_cron` + `pg_net` קוראים כל 15 דקות ל-Endpoint מוגן, והוא שולח את התזכורות שהגיע זמנן.
**השלכות:** חינמי, ודיוק של 15 דקות. הקריאות גם שומרות על פרויקט ה-Production פעיל. דורש הגדרה ידנית ב-Production.

### ADR-3: הרצת Migrations על Production דרך SQL Editor
**הקשר:** פרטי הגישה של Production לא יישמרו במחשב המקומי, והמשתמשת אינה מתכנתת.
**החלטה:** Migrations מורצים אוטומטית על Development. על Production המשתמשת מריצה אותם דרך ה-SQL Editor, לפי הדרכה ואחרי אישור, לפני ה-Push. טבלת `app_migrations` מתעדת מה הורץ בכל סביבה.
**השלכות:** אין סודות של Production במחשב, ויש שליטה מלאה של המשתמשת. הצעד הידני קצר, ומתבצע רק כשיש שינוי במבנה.

### ADR-4: התחלה בתוכנית Vercel Hobby (חינמית)
**הקשר:** תוכנית Hobby מיועדת לשימוש לא מסחרי. שימוש ארגוני עשוי לחייב תוכנית Pro (כ-‎$20 לחודש). מבחינה טכנית אין הבדל בין התוכניות לצורכי המוצר.
**החלטה:** מתחילים ב-Hobby, לפי החלטת המשתמשת. אם יידרש, עוברים ל-Pro.
**השלכות:** אין עלות Hosting בשלב זה. המעבר ל-Pro הוא שינוי בחשבון Vercel בלבד, בלי שינוי קוד.

### ADR-5: ניתוח חוזר מוסיף בלבד, עם הצעות לאישור ודוח שינויים
**הקשר:** אין דרך אמינה לזהות שפריט מניתוח חדש הוא "אותו פריט" מהניתוח הקודם. דריסה של פריטים הייתה מוחקת עריכות, שיוכים וסימוני "בוצע".
**החלטה:** ניתוח חוזר לא משנה ולא מוחק פריטים קיימים. פריטים חדשים נשמרים ב-`analysis_proposals` וממתינים לאישור. דוח שינויים בין הגרסה הקודמת לחדשה נשמר ב-`analysis_runs`.
**השלכות:** אין אובדן מידע, וההצעות שורדות סגירה של הדפדפן. פריט שהשתנה במסמכים מופיע בדוח כ"לא נמצא שוב" לצד הגרסה החדשה, והמשתמשת מעדכנת או מוחקת אותו ידנית.

### ADR-6: ימי עבודה וחגים דרך טבלת `holidays`
**הקשר:** פגישת סגירת הפינות נקבעת 3 ימי עבודה לפני ההגשה, ותזכורות שיוצאות בשישי, בשבת או בחג מוקדמות ליום חול. החישוב נעשה ב-Triggers ב-Database.
**החלטה:** טבלת `holidays` עם החגים בישראל שאינם ימי עבודה, לשנים הקרובות. הרשימה מופקת פעם אחת בעזרת `@hebcal/core` ונטענת ב-Migration. ה-Triggers מחשבים ימי עבודה לפי הטבלה.
**השלכות:** פשוט ומהיר, בלי תלות בשירות חיצוני. בעוד כמה שנים צריך להוסיף Migration עם השנים הבאות. רשימת החגים המדויקת תאושר על ידי המשתמשת בזמן הבנייה.
**עדכון (M3, אושר על ידי המשתמשת):** הימים שאינם ימי עבודה הם ימי החג, יום העצמאות **וערבי החג**: ערב ראש השנה, ערב יום כיפור, ערב סוכות, הושענא רבה, ערב פסח, ערב שביעי של פסח וערב שבועות. חול המועד נחשב יום עבודה. הרשימה כוללת את השנים 2026–2031, בסך הכול 96 ימים.

### ADR-7: כמה אחראים למשימה
**הקשר:** המשתמשת ביקשה שמשימה תוכל להיות משויכת לשני אנשי צוות או יותר, ושכולם יקבלו תזכורות.
**החלטה:** טבלת קישור `task_assignees` במקום שדה אחראי יחיד. נוצרת רשומת תזכורת לכל אחראי.
**השלכות:** בחירת האחראים בממשק היא בחירה מרובה. ה-Wireframes מציגים בחירה יחידה, ו-DESIGN.md מעודכן בהתאם.

### ADR-8: פרויקט ה-Production ב-Supabase נוצר רק ב-Milestone 8 (הפריסה)
**הקשר:** פרויקט חינמי ב-Supabase מושהה אחרי 7 ימים בלי פעילות. פרויקט Production שנוצר בתחילת הפיתוח היה מושהה חודשים עד הפריסה.
**החלטה:** ב-Milestone 1 נוצר רק `tenders-dev`. ‏`tenders-prod` נוצר ב-Milestone 8 (הפריסה). (במקור Milestone 7. המספור השתנה כשנוסף "לוח בקרה".)
**השלכות:** אין צורך להעיר פרויקט ישן. צריך לוודא שבחשבון נשאר מקום לפרויקט חינמי שני.

### ADR-9: Cache Components כבוי ב-Next.js 16
**הקשר:** תבנית ה-Next.js 16 מפעילה כברירת מחדל `cacheComponents` ו-`partialPrefetching`. כשהם פעילים, כל קריאה של ה-Session (Cookies) צריכה להיות עטופה ב-`<Suspense>`, ויש בדיקות "ניווט מיידי" נוספות. כמעט כל דף במערכת מוגן ותלוי במשתמשת המחוברת, ואין בו תוכן ציבורי שכדאי לשמור ב-Cache.
**החלטה:** כיבוי שתי האפשרויות ב-`next.config.ts`. הדפים המוגנים מוצגים מחדש בכל בקשה (Dynamic).
**השלכות:** קוד פשוט יותר, בלי Suspense סביב כל קריאת Session. ההשפעה על המהירות זניחה למשתמשת יחידה. אפשר להפעיל אותן בעתיד אם יידרש.

### ADR-10: הרצת Migrations על Development דרך `supabase db push --db-url`
**הקשר:** Claude לא קורא את `.env`, אבל צריך להריץ Migrations על פרויקט ה-Development.
**החלטה:** הסקריפט `npm run db:migrate` (‏`scripts/db-migrate.mjs`) נטען עם `node --env-file=.env` ומריץ את Supabase CLI (`db push --db-url $SUPABASE_DB_URL`). בסיום הוא מציג את השורות בטבלת `app_migrations`. שמות הקבצים בפורמט `<timestamp>_<name>.sql`.
**השלכות:** פרטי הגישה לא מוצגים ולא נקראים. ה-CLI מנהל גם רישום משלו (`supabase_migrations.schema_migrations`), בנוסף ל-`app_migrations`, שהוא הרישום שמשמש להשוואה מול Production.

### ADR-11: אייקונים מ-`lucide-react`
**הקשר:** ה-Style Guide מגדיר אייקונים קוויים, על Grid של 24px, בעובי 1.75px ועם קצוות מעוגלים.
**החלטה:** שימוש בספריית `lucide-react`, עם `strokeWidth={1.75}`.
**השלכות:** סגנון אחיד שתואם ל-Style Guide, בלי לצייר אייקונים ידנית.

### ADR-12: תפקידים בטבלה, עם הוספה מהממשק
**הקשר:** ה-PRD הגדיר 6 תפקידים קבועים. המשתמשת ביקשה אפשרות להוסיף תפקיד חדש בעצמה, בלי מסך נפרד. התפקיד הוא תווית בלבד, ושום לוגיקה במערכת לא תלויה בו.
**החלטה:** טבלת `roles` (‏key, ‏label, ‏sort_order), עם 6 התפקידים המקוריים באותם מפתחות. ‏`team_members.role` מפנה לטבלה (Foreign Key) במקום בדיקה מול רשימה קבועה. בחלון איש הצוות, האפשרות "+ תפקיד חדש…" פותחת שדה לשם התפקיד, והוא נשמר יחד עם איש הצוות. אם כבר קיים תפקיד באותו שם, משתמשים בו.
**השלכות:** אין צורך בשינוי קוד כדי להוסיף תפקיד. אין בשלב זה עריכה או מחיקה של תפקידים. אם יידרש, אפשר להוסיף זאת בהמשך.

### ADR-13: שמות הקבצים ב-Storage לפי מזהה
**הקשר:** Supabase Storage לא מקבל תווים בעברית בנתיב הקובץ, ושמות מסמכי המכרז הם כמעט תמיד בעברית.
**החלטה:** כל קובץ נשמר בנתיב `<tender_id>/<document_id>.<סיומת>`. השם המקורי נשמר ב-`tender_documents.file_name` ומוצג בממשק. כל הקבצים של מכרז נמצאים בתיקייה אחת, ומחיקת מכרז מוחקת את כל התיקייה, כולל שאריות של העלאות שנכשלו.
**השלכות:** אין בעיות עם עברית, רווחים או שמות כפולים. בלוח הבקרה של Supabase הקבצים מופיעים לפי מזהה ולא לפי שם, ואת השם מוצאים בטבלה.

### ADR-14: תאריך ההחלטה ותאריך ההגשה נקבעים ב-Trigger
**הקשר:** צריך לשמור את תאריך ההחלטה "לא ניגשים" ואת תאריך ההגשה, גם כשקופצים ישירות ל"זכינו" או ל"לא זכינו", ולא לשנות את תאריך ההגשה במעבר בין "הוגש", "זכינו" ו"לא זכינו".
**החלטה:** Trigger על שינוי `tenders.status`: מעבר ל-`not_bidding` קובע את `decided_at`, וכניסה לקבוצת `submitted` / `won` / `lost` מסטטוס שמחוץ לה קובעת את `submitted_at`. חזרה לרשימה הפעילה לא מוחקת את התאריכים.
**השלכות:** התאריכים נכונים בלי קשר למקום שבו בוצע השינוי. החלטה חוזרת על "לא ניגשים" או הגשה חוזרת מעדכנות את התאריך לתאריך החדש.

### ADR-15: OpenAI במקום Claude כשירות ה-AI
**הקשר:** באפיון נבחר Claude (ADR-1). בתחילת Milestone 3 התברר שלמשתמשת כבר יש מפתח API של OpenAI, והיא ביקשה להשתמש בו במקום לפתוח חשבון ב-Anthropic. דרישות ה-PRD נשארות: הספק לא מאמן מודלים על המידע, קריאת PDF סרוק ותשלום לפי שימוש עם תקרה חודשית.
**החלטה:** ניתוח המכרזים דרך OpenAI Responses API, עם ספריית `openai`, ‏Files API ל-PDF, ‏Structured Outputs ו-Streaming. מודל ברירת המחדל `gpt-6.1-sol`, והבחירה הסופית מתקבלת בבדיקה המקדימה. משתני הסביבה: `OPENAI_API_KEY` ו-`OPENAI_MODEL`.
**השלכות:** אין צורך בחשבון נוסף. OpenAI לא מאמנת מודלים על מידע מה-API כברירת מחדל, ושומרת בקשות עד 30 יום. העלות המוערכת נמוכה מזו של Claude. השינוי מוגבל ל-`lib/ai`, ושאר המערכת לא תלויה בספק.
**תוצאת הבדיקה המקדימה (2.11.2026):** ניתוח ניסיון של מכרז 6323: חוברת PDF של 35 עמודים, Word, ‏Excel, ‏PDF סרוק וקובץ פגום. ב-`gpt-6.1-sol` הניתוח לקח 121 שניות, והשתמש ב-133K Tokens קלט וב-10.6K פלט, בעלות של כ-$0.37. ב-`gpt-6.1-terra` הוא לקח 95 שניות, בעלות של כ-$0.17, אבל התוצאה הייתה פחות מפורטת. שני המודלים זיהו את כל המועדים, את המועד הסותר ואת הקריאה החלקית של הסריקה. המשתמשת בחרה ב-`gpt-6.1-sol`. הזמן רחוק ממגבלת 300 השניות, ולכן אין צורך לפצל את הבקשה.

### ADR-16: הניתוח רץ ברקע ומחזיר תשובה מיד
**הקשר:** ניתוח של מכרז לוקח כ-2 דקות (ADR-15). המשתמשת צריכה להיות חופשייה לעבור למסכים אחרים, ומגבלת הזמן של פונקציה ב-Vercel היא 300 שניות.
**החלטה:** ‏`POST /api/tenders/[id]/analyze` מאמת את המשתמשת, ומסמן "בניתוח" דרך `start_analysis`. הפונקציה הזו גם חוסמת הפעלה כפולה: בקשה שנייה מקבלת 409. אחרי זה הנתיב מחזיר 202 מיד, וממשיך לעבוד ברקע עם `after()` של Next.js (‏`maxDuration = 300`) ועם לקוח Supabase של השרת (Service Role). הדפדפן בודק את מצב הניתוח כל 5 שניות, ורק כשמסך המכרז פתוח. ניתוח שנמשך יותר מ-5 דקות נחשב כנכשל, ואפשר להפעיל אותו שוב.
**השלכות:** אין צורך בתור משימות או בשירות נוסף. אם הפונקציה נעצרת באמצע, המכרז נשאר במצב "בניתוח" עד שעוברות 5 דקות, ואז מוצגים פס הכישלון וכפתור "ניסיון חוזר". תוצאה של ריצה ישנה שהוחלפה בריצה חדשה נדחית, ולא נשמרת.

### ADR-17: משימה מקושרת לכל מועד, ושמירת התוצאות בטרנזקציה אחת
**הקשר:** תזכורות (M5) מתוזמנות לפי סוג המשימה, ולכן לכל מועד צריכה להיות משימה. גם ה-AI מציע משימות שמתייחסות למועדים, ולא רוצים כפילות. שמירה חלקית של ניתוח (למשל מועדים בלי משימות) תשאיר את המכרז במצב לא עקבי.
**החלטה:** הפונקציה `save_analysis` שומרת את כל התוצאות בטרנזקציה אחת: דרישות, מועדים, משימות, סעיפים בעייתיים, מצב הקריאה של כל קובץ ומספר ה-Tokens. המשימה הראשונה של ה-AI שמפנה למועד (`deadline_key`) הופכת למשימה המקושרת שלו, מאותו סוג ובאותו תאריך. מועד שאין לו משימה כזו מקבל משימה מקושרת עם שם המועד. שאר המשימות הן `regular`, עם תאריך אם ה-AI מצא, או בלי. פגישת סגירת הפינות והמשימה שלה נוצרות ב-Trigger על מועדי ההגשה, לפי מועד ההגשה המוקדם ביותר.
**השלכות:** אין מצב של שמירה חלקית. כשיש מועדי הגשה סותרים, הפגישה נקבעת לפי המוקדם מהם, והסתירה מוצגת כסעיף בעייתי. ‏`save_analysis` ו-`fail_analysis` זמינות רק לשרת (Service Role).

### ADR-18: מועד ומשימה מסונכרנים ונמחקים כזוג
**הקשר:** לכל מועד יש משימה מקושרת (ADR-17). ה-PRD דורש ששינוי תאריך באחד יעדכן את השני, ושעריכה ידנית של פגישת סגירת הפינות תמנע את ההזזה האוטומטית שלה. ה-PRD לא קבע מה קורה במחיקה. המשתמשת החליטה שהם נמחקים כזוג.
**החלטה:** Triggers ב-Database: שינוי `due_at` / `has_time` / `type` במועד מעדכן את המשימות המקושרות, ושינוי התאריך במשימה מקושרת מעדכן את המועד. עדכון מתבצע רק כשיש הבדל, כדי למנוע לולאה. עריכה ידנית (`is_manual`) של אחד מהם מסמנת גם את השני, ולכן פגישת סגירת פינות שנערכה לא זזה יותר. מועד שנוסף ידנית מקבל משימה מקושרת אוטומטית. מחיקת מועד מוחקת את המשימה (`on delete cascade`), ומחיקה ישירה של משימה מקושרת מוחקת את המועד שלה. מחיקה ידנית של הפגישה האוטומטית מסמנת `tenders.closing_meeting_dismissed`, והפגישה לא נוצרת שוב באותו מכרז. מחיקה פנימית, כשמועד ההגשה נמחק, לא מסמנת.
**השלכות:** הסנכרון נכון בלי קשר למקום שבו בוצע השינוי, וזה גם הבסיס לתזכורות של M5. חלונות האישור במחיקה אומרים שגם הפריט המקושר יימחק.

### ADR-19: ניתוח מחדש — מזהים קצרים, `missing_ids` והצעות לאישור
**הקשר:** ניתוח מחדש לא משנה פריטים קיימים (ADR-5). צריך לזהות אילו פריטים חדשים, ואילו פריטים קיימים כבר לא נתמכים במסמכים, בלי לשלוח ל-AI מידע פנימי.
**החלטה:** ‏`start_analysis` מסמנת ריצה כניתוח מחדש (`analysis_runs.is_reanalysis`) כשכבר יש למכרז ריצה מוצלחת. בניתוח מחדש השרת שולח ל-OpenAI, יחד עם המסמכים, רשימה של הפריטים הקיימים בטקסט בלבד, עם מזהה קצר לכל פריט (`R`, ‏`D`, ‏`T`, ‏`I`). אין בה אחראים, "בוצע" או מועדי תזכורת. המודל מחזיר רק פריטים חדשים, ובנוסף `missing_ids`. השרת מתעלם ממזהים לא מוכרים ומפריטים ידניים, כי הם לא באו מהמסמכים. ‏`save_reanalysis` שומרת את הפריטים החדשים ב-`analysis_proposals` ואת דוח השינויים (`added` ו-`missing` עם תווית קריאה), ולא נוגעת בפריטים הקיימים. ‏`accept_proposals` מוסיפה את מה שסומן ודוחה את שאר ההצעות הממתינות של אותה ריצה. מועד שאושר מקבל משימה מקושרת לפי אותו כלל של `save_analysis`. "לא עכשיו" משאיר את ההצעות ממתינות.
**השלכות:** אין אובדן של עריכות, שיוכים וסימוני "בוצע" (נבדק: הפריטים זהים לפני ואחרי). פגישת סגירת הפינות נשארת לפי מועד ההגשה המוקדם ביותר, ולכן מועד הגשה שנדחה מופיע כמועד חדש, והמועד הישן מופיע ב"לא נמצאו שוב". המשתמשת מוחקת אותו ידנית, והפגישה זזה. ניסיון ראשון על מכרז קטן עלה כ-$0.04.

### ADR-20: תזכורות נבנות מחדש בכל שינוי
**הקשר:** תזכורות צריכות להיווצר, להתבטל ולזוז בהרבה מצבים: שינוי מועד, סוג או מועד תזכורת, שיוך או הסרה של אחראי, "בוצע", "ללא תזכורת" ושינוי סטטוס המכרז. Trigger נפרד לכל מקרה מסובך ועלול לפספס מצבים. בנוסף, המשתמשת החליטה: תזכורת שנופלת בשישי, בשבת או בחג מוקדמת ליום העבודה הקודם באותה שעה; תזכורת שהתעכבה נשלחת רק אם מועד המשימה עוד לא עבר; ולכל משימה מסוג קבוע אפשר לבחור "ללא תזכורת".
**החלטה:** הפונקציה `rebuild_task_reminders` מבטלת את כל התזכורות הממתינות של המשימה ויוצרת אותן מחדש לפי המצב הנוכחי, עם הזמנים מ-`reminder_slots` ו-`shift_to_workday`. כל ה-Triggers הרלוונטיים (על `tasks`, ‏`task_assignees` ו-`tenders.status`) קוראים לה. משימה שבוצעה, משימה עם `tasks.reminders_off` ומכרז שאינו "בבדיקה" או "בהכנה" לא מקבלים תזכורות. השליחה עוברת דרך `claim_due_reminders`, שמבטלת תזכורות שכבר לא רלוונטיות (כולל תזכורת שאיחרה ביותר מ-30 דקות כשמועד המשימה עבר), ומסמנת `claimed_at` כדי ששתי הפעלות לא ישלחו אותה תזכורת פעמיים. נוספו לטבלה `recipient_email` (הכתובת שאליה ניסינו לשלוח, נשמרת ברגע השליחה) ו-`handled_at` ("סימון כטופל" בחלון הכשלים).
**השלכות:** כל שינוי, מכל מקום, משאיר את התזכורות נכונות, וקל לבדוק את הכללים. תזכורות שנשלחו או נכשלו נשמרות כהיסטוריה. כתובת לא קיימת בדומיין תקין מתקבלת על ידי Gmail ונדחית רק אחר כך (Bounce) — הדחייה מגיעה לתיבה של `GMAIL_USER` ולא מופיעה בפס הכשלים.

### ADR-21: קישור איפוס סיסמה עם `token_hash`
**הקשר:** ברירת המחדל של Supabase לאיפוס סיסמה עובדת רק באותו דפדפן שבו ביקשו את האיפוס (PKCE). המשתמשת עשויה לבקש איפוס במחשב ולפתוח את המייל בטלפון.
**החלטה:** הקישור בתבנית המייל מוביל ל-`/auth/confirm?token_hash=...&type=recovery&next=/reset-password`, והשרת מאמת אותו עם `verifyOtp`. קישור לא תקין או שכבר נוצל מוביל ל-"שכחתי סיסמה" עם הודעה שהקישור פג. התבנית העברית נמצאת ב-`supabase/email-templates/reset-password.html`.
**השלכות:** האיפוס עובד מכל מכשיר. התבנית ו-Custom SMTP צריכים להיות מוגדרים ידנית ב-Supabase, גם בפרויקט ה-Production (M8).

### ADR-22: סיכום משותף לייצוא ולמייל, ומייל נפרד לכל נמען
**הקשר:** ב-Milestone 6 אותו תוכן (ארבעת חלקי הסיכום) מוצג בשלושה מקומות: קובץ Word, עמוד ההדפסה ל-PDF וטיוטת המייל. השליחה במייל יכולה להיות לכמה נמענים, חלקם כתובות שהוקלדו ידנית.
**החלטה:** `lib/summary.ts` טוען את הסיכום פעם אחת, עם הטקסט המוכן לתצוגה, ומשמש את שלושת המקומות. עמוד ההדפסה נמצא בנתיב `/print/tenders/[id]`, מחוץ ל-App Shell, ופותח את חלון ההדפסה אוטומטית רק כשמגיעים מ"PDF (הדפסה)" (`?auto=1`). טיוטת המייל נטענת דרך Server Action (`getEmailDraft`). השליחה ב-`POST /api/tenders/[id]/email` שולחת מייל נפרד לכל נמען, ובודקת את כל הכתובות לפני ששולחת משהו.
**השלכות:** Word, PDF ומייל תמיד מציגים אותו תוכן ובאותו ניסוח. הנמענים לא רואים זה את הכתובות של זה, וכתובת שנדחתה לא מכשילה את השליחה לאחרים; החלון מציג למי לא נשלח ומשאיר רק אותם לניסיון חוזר. מספר הנמענים בשליחה מוגבל ל-20.

### ADR-23: אחראים ותזכורות ישירות בלוח הזמנים, ותזכורת אוטומטית ל"מועד אחר"
**הקשר:** המשתמשת רצתה לבחור אחראי לכל שורה בלוח הזמנים ולקבל תזכורת אוטומטית לכל מועד, בלי לעבור ללשונית משימות ובלי לקבוע מועד תזכורת ידנית. עד עכשיו "מועד אחר" קיבל תזכורת רק אם הוזן לו מועד תזכורת.
**החלטה:** לשונית לוח הזמנים מציגה לכל מועד את האחראים ותיבת "תזכורת" של המשימה המקושרת אליו, ושומרת ישירות עליה (`task_assignees`, `reminders_off`). אין טבלה חדשה. ב-`reminder_slots`, משימה מסוג `other` בלי `remind_at` מקבלת תזכורת יום לפני המועד (בשעת המועד, או 08:00), לאחראים בלבד, כמו הסוגים הקבועים. מועד תזכורת ידני עדיין גובר. משימה `regular` לא השתנתה (Migration ‏`20261104120000_m6_other_reminders`).
**השלכות:** כל מועד בלוח הזמנים מתוזמן אוטומטית ברגע שיש לו אחראי, וביטול נעשה בתיבה אחת. משימות כלליות שה-AI מפיק לא מציפות את המשתמשת בתזכורות. ה-Migration צריך לרוץ גם על Production לפני הדחיפה.

### ADR-24: רשימת משימות מלאה, ותזכורות רק ממה שבלוח הזמנים
**הקשר:** אותם פריטים הופיעו בשתי לשוניות עם עריכה בשתיהן, וזה בלבל את המשתמשת. היא ביקשה שכל המשימות יישארו ברשימה, ושרק מה שנמצא בלוח הזמנים ישלח תזכורות. לוח הזמנים מתמלא אוטומטית רק מהסוגים הקבועים.
**החלטה:** הטבלאות נשארות. שורה ב-`deadlines` עם משימה מקושרת היא "בלוח הזמנים". ‏`rebuild_task_reminders` יוצר תזכורות רק כש-`deadline_id` מולא. "מועד אחר" שמגיע מניתוח מתנתק ב-Constraint Trigger דחוי (`deadlines_detach_other`), שרץ בסוף הטרנזקציה ולכן מכסה גם `save_analysis` וגם `accept_proposals` בלי לשנות אותן: המשימה נשארת `regular` עם התאריך ועם `source_refs`. ‏`add_task_to_timeline` יוצר מועד ומקשר אליו את המשימה, ו-`remove_from_timeline` מנתק ומוחק את המועד בלי למחוק את המשימה. בלשונית משימות התאריך והתזכורת לקריאה בלבד (Migration ‏`20261104140000_m6_timeline_model`).
**השלכות:** כל פריט נערך במקום אחד. משימה רגילה לא מקבלת תזכורת, וחלון המשימה פשוט יותר. נתונים קיימים: מועד אחר מניתוח בלי אחראי ובלי מועד תזכורת יורד מלוח הזמנים, ומשימה עם מועד תזכורת נכנסת אליו. חלון "נמצאו פריטים חדשים" עדיין מציג מועד אחר תחת "מועדים", אבל באישור הוא הופך למשימה. ב-`lib/summary.ts` חלק "משימות" כולל רק משימות בלי `deadline_id`, וחלק "לוח זמנים" מציג גם אחראים ומצב. ה-Migration צריך לרוץ גם על Production לפני הדחיפה.

### ADR-25: לוח בקרה בלי שינוי Database ובלי ספריית גרפים
**הקשר:** לוח הבקרה (Milestone 7) מציג מדדים ושני גרפי עמודות פשוטים, בלי צירים, רשת או מקרא. הוא חייב להתאים בדיוק לרשימות הקיימות ("מכרזים פעילים", "הוגשו" וה-Badges של האיחורים), וכל החישובים הם לפי שעון ישראל.
**החלטה:** המסך בכתובת `/dashboard`, והכתובת הראשית, ההתחברות ושמירת סיסמה חדשה מפנות אליו. שאילתה אחת טוענת את המכרזים, ו-`lib/dashboard.ts` מחשב מהם את כל המספרים, עם אותן פונקציות של הרשימות (`isOverdue`, `earliestSubmission`). הגרפים הם HTML ו-CSS בלבד, בלי ספרייה. פס "תזכורות לא נשלחו" מוצג בלוח הבקרה וב"מכרזים פעילים", דרך `lib/failed-reminders.ts`, ומציג רק כשלים של מכרזים פעילים (החלטת המשתמשת).
**השלכות:** אין Migration ואין תלות חדשה. המספרים לא יכולים להתפצל מהרשימות. אם בעתיד יידרשו גרפים מורכבים יותר, אפשר להחליף רק את `MonthBars`. כשל של מכרז שיצא מהרשימה הפעילה לא מוצג, ויחזור להופיע אם המכרז יחזור אליה.
